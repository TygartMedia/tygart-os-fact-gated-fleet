# Reverse MCP Landscape — Research Report

Read date: 2026-11-03. Flags: **verified live** = page opened and read directly in the research browser; **index** = search-index result/read, not opened live. Vendor accuracy/funding claims are flagged as marketing/secondary where the source allows.

**Pattern tested (5 parts):** (1) one intake for messy unstructured inputs; (2) verification/grounding against sources by a *separate* checker (proposer ≠ approver); (3) output *only* through per-destination, learned, versioned “output profiles” (schema/vocabulary/format/import/API shape of one destination) — destination provides no special integration, same verified content emitted in many shapes; (4) destination read-back confirmation per output; (5) profiles start on probation and earn trust after verified deliveries. Inventor terms: “reverse MCP”, profiles = “tips”.

## Summary

- **The full 5-part pattern has not been built anywhere public that this research could find.** Every candidate is strong on 2–3 parts and missing the same three: an independent grounding gate, per-destination probation/trust staging, and destination read-back confirmation.
- **“Reverse MCP” is not used for this meaning anywhere public.** All uses found mean reverse *engineering*, reverse *shells*, reverse *tunneling*, or (one case) a mislabelled ordinary MCP connection. The term is unclaimed for this meaning but polluted — a builder using it will be misunderstood by searchers as a security/reverse-engineering tool.
- **Furthest along, by part:** superglue for “declared target schema constrains LLM-generated mapping, deterministically validated, self-healing”; Flatfile (now Obvious) for learned per-destination templates at scale; Extend for grounded extraction + a separate Review Agent + evals/versioning; EDI/HL7-FHIR tooling (Health1st, ArghaHealth, and classic X12) for per-partner mapping profiles *and* the only real read-back in the wild (997/999/824 acknowledgments); Encircle/DocuSketch in the restoration vertical for capture → one/two carrier shapes, with DocuSketch’s AskAiME checking against *carrier-specific* requirements.
- **“Starting where they’re at” concretely:** adopt superglue’s architecture (and talk to the company — it now sells hosted ERP-implementation agents) + Flatfile/OneSchema-style learned mapping UX + Extend’s eval/review-agent gate as composable pieces; there is no single partner who has the whole loop.

### 2. Companies/products closest to the full pattern or its parts

**Unified-API / integration platforms — all “forward MCP”, philosophy inverted vs. the pattern.** They succeed because the destination *did* provide an API/integration; the model reaches out through pre-built tools. None learns a destination’s shape from deliveries, none gates content by independent grounding, none does read-back of business content.

- **Composio / Tool Router** — agentic integration platform, one MCP endpoint to 1,000+ apps / 20,000+ tools; Tool Router (beta Oct 2025, later GA) creates per-user session URLs and surfaces only relevant tools via meta-tools (search, plan). $29M total: $4M seed + $25M Series A led by Lightspeed, announced 2025-07-22; 200+ paying companies, $1M+ ARR at raise (trade press). **index:** https://chatforest.com/reviews/composio-mcp-server/
- **Merge** — unified API: hand-built *common/normalized models* per category (HRIS, ATS, CRM, accounting…) across 250+ integrations — the deliberate opposite of per-destination profiles (one model, not many shapes). Merge Agent Handler (Oct 2025) adds MCP-ready connectors for agents. ~$74.5M total funding per secondary sources; 7,000+ customers claimed. **index:** https://getknit.dev/blog/understanding-merge-dev-pricing-finding-the-right-unified-api-for-your-integration-needs/
- **Nango** — open-source integration platform, 1,000+ APIs, AI-assisted connector building via coding agents; usage pricing. No learned output profiles. Covered comparatively at **index:** https://agentsindex.ai/blog/agent-to-app-connectivity-platform-comparison
- **Arcade.dev** — “secure action layer / MCP runtime”: delegated per-user authorization, policy hooks, audit logs; authored MCP authorization spec work. $12M seed (2025) + $60M Series A led by SYN Ventures (June 2026) = $72M total; claims production at a top US bank, Prosus, LangChain (vendor claims in the funding release, not independently verified). Its gate checks *permission*, not *content grounding*. **index:** https://www.hpcwire.com/aiwire/2026/06/16/arcade-secures-60m-to-scale-authorization-and-governance-for-ai-agents/
- **Zapier / Workato / Tray / Boomi / Pipedream** — iPaaS: 1,000–9,000+ pre-built connectors, recipes, data mapping by hand, now with MCP gateways/agent builders bolted on (Zapier MCP gives agents governed access to its connector library; Workato 1,000+ connectors + agentic orchestration; Boomi strong in legacy/EDI). Pipedream was reportedly absorbed by Workday in late 2025 per secondary research notes — treat as unverified. None learns per-destination profiles from verified deliveries. **index:** https://zapier.com/blog/workato-vs-boomi/

**Structured-output / constrained generation — part 3’s mechanism, minus learning, delivery, and destinations.** Instructor validates LLM output against a Pydantic model and re-prompts on failure; Outlines guarantees JSON-Schema/regex/grammar conformance *during* generation via finite-state constrained decoding; Guidance interleaves grammar-constrained generation; BAML is a schema-as-contract DSL with schema-aligned parsing; Guardrails AI validates outputs with reusable validators and corrective re-asking. In every case the schema is supplied once by a developer — it is not learned per destination, not versioned from delivery history, and nothing is delivered or read back. **index:** https://github.com/qte77/ai-agents-research/commit/6e6074c5c44aa0974a997f2e16b446b428bf6eab and https://www.aicassindra.com/blogs/prompt_engineering/pe_structured_output.html

**Document-AI extraction — parts 1 and 2 (human version), not 3–5.**

- **Extend** — see §3.
- **Rossum** — see §3.
- **Nanonets** — OCR + model-per-document-type extraction, approval queues, validation rules, ERP integrations, human-in-the-loop; now also sells AI agents with extraction as one step. Requires training per document type. **index:** https://dev.to/iterationlayer/best-document-extraction-apis-in-2026-32gb
- **Mindee / LlamaParse (LlamaExtract)** — extraction/parsing APIs returning fields or markdown with citations; the review/verification layer is explicitly “you build it” per comparative reviews. They are intake components, not destination emitters. **index:** https://medium.com/@rushabh.sheth_51878/the-best-document-data-extraction-api-to-embed-in-your-own-software-2026-673b7c46f98f

**Agent computer-use / UI-driving — a delivery *mechanism* for part 3, with no profiles.** Anthropic Computer Use (Oct 2024, screenshot → click/type loop), OpenAI Operator/CUA (Jan 2025), MultiOn, Browser Use, Skyvern let an agent fill forms in systems with no API — exactly how a “tip” would deliver into a form-only destination — but the shape knowledge lives in the agent’s runtime reasoning, not in a learned, versioned, probationed profile, and confirmation is just the next screenshot. Adept effectively exited as an independent agent company (talent deal era) and MultiOn pivoted toward vertical browser workflows; neither markets destination profiles. **index:** https://haozhe-xing.github.io/agent_learning/en/chapter_25_multimodal/05_computer_use_agent.html

**AI field-mapping in ETL/ELT and data import — part 3’s closest commercial ancestors.**

- **Flatfile → Obvious, OneSchema, Osmos, Dromo** — see Flatfile in §3. OneSchema: embeddable importer + file automation, AI-generated transformation code, *reusable templates and customer-specific overrides*, PDF extraction and Salesforce read/write on supported accounts (**index:** https://www.rocketlane.com/blogs/best-data-migration-tools). Osmos: AI transformation engine that cleans/reformats incoming files “to match your destination schema” (**index:** https://SourceForge.net/software/product/Impler/alternatives).
- **Fivetran / Airbyte / Hevo / Stitch** — AI is limited to suggested/automatic schema mapping, schema-drift handling, and pipeline copilots; Fivetran explicitly does transformation downstream in dbt, Airbyte has no native field-level AI transformation per comparative testing. Their destinations are warehouses with vendor-built connectors. **index:** https://www.integrate.io/blog/ai-etl-tools/
- **dlt / dltHub** — open-source (Apache-2.0) Python load library: schema inference/evolution, schema contracts, verified sources, destination = a parameter; commercial dltHub adds an AI harness/MCP tooling for coding agents to build pipelines. A buildable substrate for tips, not a tips product. **index:** https://dlthub.com/docs/hub/getting-started/oss-and-dlthub

**HL7/FHIR and EDI — the oldest version of this problem, and the closest analogue overall for parts 3+4.** For decades, EDI mapping has meant a *per-trading-partner implementation/companion guide* (that partner’s exact dialect of X12) and a translator that emits only that shape — a hand-built, versioned “tip”. The read-back is standardized too:

- **X12 997 Functional Acknowledgment** confirms receipt and *syntax* acceptance/rejection with segment/element error detail; **999** adds implementation-guide rules; **824 Application Advice** carries business-level acceptance/errors. A 997 alone does *not* prove business acceptance — an important precision for any read-back design. **index:** https://www.seeburger.com/resources/good-to-know/ansi-x12-edi-997-technical-acknowledgement-message
- **Health1st** — “AI-native” any-format ↔ any-format translation (HL7v2, FHIR R4/R5, C-CDA, X12, NCPDP, DICOM, flat files): “AI maps it; your team approves it, with a full audit trail”; “AI drafts the mappings and normalizes the codes; your analysts review and approve before anything ships”; FHIR R4.0.1 validation claimed. Vendor claims, early-stage appearance. **index:** https://www.health1st.ai/
- **ArghaHealth** — any source (HL7/EDI feeds, CSV, payer portals, APIs) → FHIR R4 or any target: LLM schema detection “learns your data… and maps it automatically, with confidence scores on every field”, team confirms the mapping, “every integration makes the mapping engine smarter”. **index:** https://arghahealth.com/
- Classic integration engines (Mirth Connect, Redox, InterSystems, Boomi B2B/EDI) do per-partner mapping and acknowledgments deterministically, without LLM learning — the incumbent baseline a “reverse MCP” builder would displace.

**Salesforce/HubSpot import AI** — no dedicated category leader found beyond the importers above (OneSchema’s Salesforce connectivity, Flatfile/Osmos/Dromo CRM imports, Merge’s CRM unified API). HubSpot/Salesforce native import tools do column matching and duplicate checks, not learned per-destination profiles with verification gates.

### 4. Academic / standards work

- **MCP itself (output side)** — The MCP spec’s only output-shaping primitive is a tool’s optional `outputSchema`: “a server providing one must return conforming structured results.” The 2025-11-25 revision also added elicitation and Tasks. Nothing in MCP, **A2A** (agent↔agent delegation: Agent Cards, tasks, artifacts; 1.0 released Mar 2026), or **AG-UI** (agent↔user event stream) covers learned per-destination profiles, delivery confirmation, or trust staging — they standardize how a model *reaches* tools/agents and how results *return*, not how a destination’s learned shape constrains emission. **index:** https://research.notelligent.app/en/2026-03-28-open-agent-protocol-stack.html
- **API-calling LLMs (forward direction)** — Gorilla (Patil et al., NeurIPS 2024; arXiv:2305.15334) retrieves current API docs to produce correct calls for hundreds of APIs and reduce hallucination as specs change; ToolLLM/ToolBench (ICLR 2024; arXiv:2307.16789) trains on 16,000+ real REST APIs; RestGPT (arXiv:2306.06624) parses REST descriptions, plans, and generates/executes calls + response transforms. All teach a model to *conform to a given API at call time* — the intellectual parent of a “tip”, without learning/versioning/probation across deliveries. Summarized at **index:** https://raw.githubusercontent.com/mlresearch/v306/main/assets/marro26b/marro26b.pdf
- **“Universal adapter” position paper** — Marro & Torr, *LLM Agents Are the Antidote to Walled Gardens*: an LLM-based universal adapter “dynamically discovers available operations, infers schema mappings, and generates the necessary glue code or UI actions at runtime, eliminating dependence on preprogrammed integrations”, citing RestGPT/Gorilla as evidence. This is the closest academic framing of the reverse-MCP thesis — but it argues for *runtime-generated, disposable* adapters, the opposite design choice from learned, versioned, probationed profiles. Same source as above.
- **LLM schema matching** — a named, surveyed subfield: MatchGPT, ReMatch, Prompt-Matcher, Matchmaker, Magneto, KcMF, etc., surveyed in *Can LLMs Clean Up Your Mess? A Survey of Application-Ready Data Preparation with LLMs* (IEEE TKDE; arXiv:2601.17058), which defines schema matching as learning correspondences between source and target schemas and notes persistent hallucination and weak evaluation as open problems. No surveyed work adds delivery, read-back, or trust staging. **index:** https://arxiv.org/html/2601.17058v1/
- **Constrained decoding** — Outlines/Guidance-style grammar/FSM-constrained generation and the XGrammar line of work guarantee *syntactic* conformance to a supplied schema; the structured-output literature is explicit that this guarantees shape, not semantic correctness — “validate the semantics yourself” — i.e., academia supplies part 3’s enforcement mechanism and explicitly leaves part 2 (grounding) to the builder. **index:** https://www.aicassindra.com/blogs/prompt_engineering/pe_structured_output.html

### 6. Bottom line synthesis

**Has the full pattern been built anywhere public? No.** Across unified APIs, iPaaS, document AI, ETL/import, EDI/FHIR, structured-output tooling, computer-use agents, and the restoration vertical, no public product was found that combines all five parts — and in particular no one was found marketing (a) a checker that is a *different model/role* from the proposer as a named separation-of-duties gate (Extend’s Review Agent and superglue’s deterministic validator are the two nearest mechanisms), (b) *probation/trust staging of a per-destination profile* (the IDP straight-through-processing loop is the nearest behaviour, per document type, not per destination), or (c) *destination read-back confirmation* outside EDI’s 997/999/824 acknowledgments and FHIR validation.

**Single furthest-along thing:** it depends which half of the pattern you weight —

- For the *output-profile core (part 3)*: **superglue** is furthest along conceptually — declared target schema → LLM-generated mapping → deterministic cached transform → schema validation → self-healing remapping. But its OSS repo is now deprecated and the company has pivoted to hosted ERP-implementation agents, and its direction is inbound (source → your schema), not verified content → many destinations.
- For a *commercially mature, contactable* embodiment of learned per-destination templates: **Flatfile/Obvious** (with OneSchema as the more focused alternative) — a decade of mapping memory at billion-row scale, but files-in/files-out, human checker, no grounding against source documents, no read-back, no probation.
- For the *verification half (parts 1–2)*: **Extend** — citations, confidence routing, eval sets, versioned processors, and a separate Review Agent.

**What “starting where they’re at” concretely looks like:**

1. **Learn from / talk to superglue first** ([public contact email redacted — see superglue.cloud] per its YC page; hosted trial at app.superglue.cloud). Ask specifically about their target-schema + JSONata mapping-program + drift self-healing internals and whether the hosted ERP-agent product will emit *into* destination shapes. Do **not** build on the deprecated GitHub repo.
2. **Adopt the importer segment rather than rebuilding it:** evaluate Flatfile/Obvious and OneSchema for the learned-mapping UX and mapping-program representation (a versioned, saveable mapping artifact is exactly what a “tip” needs to be). Their mapping-memory approach (learn from past selections, predict the next) is the proven way to bootstrap a profile.
3. **Adopt Extend’s gate as the part-2 reference design** (or Extend itself for document intake): per-field citations + confidence, eval sets per processor version, a checker agent separate from the extractor, human review only for routed exceptions. This is the closest shipped version of “proposer never approves its own work”.
4. **Copy EDI’s read-back semantics, not its syntax:** require a 997-style syntax ack, a 999-style profile-conformance ack, and an 824-style business-acceptance ack as three distinct states for every destination — the vertical and integration incumbents already think in these layers, and conflating them is the classic failure.
5. **Build the two genuinely novel pieces yourself — they appear to be the defensible core:** (i) per-destination profile *probation → trust* lifecycle driven by verified deliveries (borrow IDP straight-through thresholds as the mechanism, keyed by destination instead of document type), and (ii) read-back verification as a first-class step for non-EDI destinations (API re-fetch, portal screenshot via computer-use, or import-file acceptance report).
6. **In the restoration vertical, start from Encircle + DocuSketch’s reality:** the market already accepts “one capture → ESX for Xactimate / FML for Cotality, checked against carrier-specific requirements (AskAiME)”. A builder offering the same capture emitted to DASH/PSA/Restoration Manager/QuickBooks shapes — destinations DocuSketch notably does *not* natively reach — with a carrier-profile probation history would be differentiated on day one, and Encircle/DocuSketch/Verisk are the partnership conversations to have.
